<ul class="space-y-2 text-[15px] text-accent-gray-800 leading-relaxed list-disc pl-5">
<li><strong>「落地鸿沟」被一组硬数据量化了</strong>：1906 份有效问卷显示，已开发完成或开发中的企业合计 <strong>46%</strong>（去年 36%），但真正部署到生产环节的只有 <strong>18%</strong>，持续迭代的不到 10%。白皮书的判断是：卡点不在意愿，也不在模型能力，而在「能优化 Harness 层、开箱即用的工程配套」。</li>
<li><strong>Agent = Model + Harness</strong>：全书的抽象地基。Model 负责理解、推理、生成与决策；Harness 是模型之外用于组织、约束并承载执行的工程系统，落地时拆为 Agent Loop｜Context、State 与 Memory｜Tool、Skill 与 Protocol｜Runtime 与 Sandbox｜Observability 与 Evaluation｜Security 与 Governance 六类能力。这条公式直接决定责任边界——模型升级不应变成应用重构。</li>
<li><strong>形态不是替代链，成熟度不由产品名称决定</strong>：Chat/RAG、Workflow、Copilot、Single-Agent、Long-Horizon Agent、Multi-Agent 长期共存；配套的 L1–L4 成熟度模型主张「为每类任务选择成本与风险可接受的最低充分架构」，而不是级别越高越好。</li>
<li><strong>最被低估的短板是评估</strong>：55% 的企业靠人工抽查判断 Agent 好不好用，能基于运行轨迹（Trajectory）自动评估的只有 6%（报告概述处表述为「不足 8%」），16% 的受访者从未量化过任务成功率。而用上评估手段的企业，任务成功率达 70% 以上的比例是无评估体系企业的约两倍。</li>
<li><strong>AI 网关是被调研验证的刚需</strong>：多模型路由与自动降级被 63% 的企业列为最需要的网关能力，是本次调研<strong>比例最高的单项需求</strong>。白皮书把 AI Gateway 拆成 LLM / MCP / Agent 三种治理语义，明确三者治理粒度不能混同。</li>
<li><strong>MCP 差的是企业级配套，不是协议理解</strong>：已关注或已落地 MCP 的企业合计 37%，真正完成企业内私有部署的只有 9%——缺的是私有注册中心、统一身份鉴权、版本灰度、审计留痕与网关集成。</li>
<li><strong>Agentic OS 是「一组正在成形的系统职责」，不是已有产品</strong>：第 30 章明确声明它「现在还不是一个已经存在的产品类别，也不必然对应一个新的内核」。这个限定词在二手转述中经常被丢掉。</li>
<li><strong>实践篇是这一版最大的增量</strong>：16 篇真实企业案例（吉利汽车、哔哩哔哩、MiniMax、信永中和、塔斯汀、畅捷通、PolarDB-X、Kitta、ABACI、PatchPilot 等）+ GOAI 开源大赛 Agent Infra 赛道 15 项决赛作品，覆盖 11 个互不重合的行业领域。</li>

## 背景：为什么一年之内要重写一本白皮书

2025 年 9 月，阿里云发布了[《AI 原生应用架构白皮书》](https://developer.aliyun.com/ebook/8479)，围绕 AI 原生应用的 DevOps 全生命周期，从架构设计、技术选型、工程实践到运维优化做体系化拆解。一年之后的 2026 云栖大会 Agentic 技术主论坛上，这本书被整体推翻重写，并以**开源仓库**的形式发布——这本身就是一个信号：作者团队认为旧版的组织方式已经无法承载新问题。

白皮书在前言与 README 中给出的理由很直接：市场的关注度已经从「快速构建智能体」转向三大新挑战。

| 新挑战 | 原文表述 | 翻译成管理者语言 |
| --- | --- | --- |
| **工程化挑战** | 从概率智能到可靠生产力，Agent 能够承担关键任务 | Demo 能跑不等于能交付，概率系统怎么进严肃流程 |
| **规模化挑战** | 稳定、安全、性能、成本，从单点试验到智能基础设施，Agent 能够被大规模部署 | 从 1 个 Agent 到 100 个 Agent，基础设施与成本模型要重建 |
| **组织化挑战** | 从 Agent 孤岛到智能组织，Agent 能够进入核心业务流程 | Agent 之间、Agent 与人之间的协作与责任边界问题 |

原文对旧版的评价只有一句话：「去年的那本白皮书，显然难以应对这些新的诉求。」

前言里还有一段值得单独摘出来的自我拷问——在 AI 能分分钟生成十本白皮书的当下，人写白皮书还有没有价值。作者团队给出的答案是四类**稀缺物**：

> **自洽的概念和语言**：Harness、Runtime、Agent、Workflow 这些词，不同人、不同视角，讲的可能并不完全是一件事。AI 会放大这种混乱。
>
> **判断**：模型很擅长把已经存在的信息重新组织成通顺的表达，但它提供的，往往是一个看起来很合理的平均值。
>
> **经验**：某个系统在真实生产环境里到底发生过什么，什么地方反复出问题，这些来自一线工程师的一手经验，AI 很难替代。
>
> **教训**：内容越是丰富，什么不该做就比什么可以做更稀缺。真实的失败模式是从实际生产环境人为提炼出来，不是语言模型顺着上下文续写出来的。

这四条其实也是本文选择做**导读而非摘要**的理由：这本书里真正有价值的部分，是那些「不能靠推理补全」的东西——调研数据、概念边界、失败模式、企业案例里的具体取舍。

白皮书整体结构是「架构 → 构建 → 运行 → 治理 → 调优」五阶段生命周期，加上前置的调研报告、后置的实践篇与总结展望篇，共 30 章、约 50 万字（据本站统计，白皮书原文未公布字数）。

## 一、《2026 Agent 开发者调研报告》：1906 份问卷的硬数据

这份调研报告放在全书正文之前，是整本白皮书的**问题定义来源**——后面所有章节的设置，都可以回溯到这里的某个痛点。数据采集方式：在北京、深圳、广州、上海、杭州等城市举办多场线下开发者沙龙，回收**有效问卷 1906 份**，受访者以企业的技术决策者、架构师、一线工程师和产品经理为主。

对中国区企业和跨国公司的技术决策者来说，这是目前少见的、以**中国大陆企业样本为主**的 Agent 落地现状量化数据，值得逐项对照自己的组织。

### 1.1 投入已成共识，生产化仍是少数派

![图 1 三城 Agent 开发状态分布：北京、广州、深圳三城分列，图例为「已上线并持续迭代 / 开发中 / 计划开发 / 暂无开发计划」](/learn/aliyun-ai-agent-handbook/survey-adoption.png)

*图：原报告「图 1 三城 Agent 开发状态分布」，按北京、广州、深圳**三城分列**展示四类开发状态（已上线并持续迭代 / 开发中 / 计划开发 / 暂无开发计划）。原图出自《2026 Agent 开发者调研报告》第二节，1906 份有效问卷。下表的全国合计数出自报告正文，非本图直接读数。*

| 指标 | 2025 年 | 2026 年 | 变化 |
| --- | --- | --- | --- |
| 明确表示暂无开发计划 | 22% | **15%** | ↓ 7pt |
| 正在调研 / 计划开发 | 47% | **25%** | ↓ 22pt |
| 已开发完成或开发中（合计） | 36% | **46%** | ↑ 10pt |
| **真正部署到生产环节** | — | **18%** | — |
| 已上线并持续迭代 | — | **不到 10%** | — |

这组数字的含义是：**「要不要做 Agent」已经不再是议题，「能不能上生产」才是**。46% 在做、18% 上生产、不到 10% 在持续迭代——每一级都在腰斩。

> 📌 **本站核对提示**：15% + 25% + 46% = 86%，原文未说明剩余约 14% 的归属（可能为多选口径或未作答）。引用时建议保留「合计 46%」这一原文表述，不要反推分布。

### 1.2 卡住的不是意愿，是工程能力储备

报告用地域 × 企业规模的交叉数据给出了一个很硬的结论：**上线率的差距普遍大于开发率的差距**。

| 城市 | 大型企业已上线率 | 小微企业已上线率 | 差距 |
| --- | --- | --- | --- |
| 上海 | **45%** | **16%** | 29pt |
| 深圳 | **38%** | **17%** | 21pt |

原文的解读是：「差异并不在是否愿意投入，而是是否具备持续演进 Agent 的工程能力，包括 Agent 的组织和协作、治理、优化和沉淀等。」

这一条对咨询与集成服务商意义很直接——**29 个百分点的差距不是模型差距，是工程能力差距，而工程能力是可以被外部供给的**。

### 1.3 单 Agent、多 Agent、人在回路：三种选择长期共存

![图 3 主要采用的架构模式：按城市分列的柱状图，四类为多 Agent 协作（编排）、单 Agent 架构、Agent+人类协作 HITL、Agentic RAG 架构](/learn/aliyun-ai-agent-handbook/survey-architecture.png)

*图：原报告「图 3 主要采用的架构模式」，按城市**分列**的柱状图，四类架构为多 Agent 协作（编排）、单 Agent 架构、Agent + 人类协作（HITL）、Agentic RAG 架构，各城柱值在 3.0%–44.4% 区间。下表为报告正文给出的全国合计口径，与本图分城读数不是同一组数字。*

| 主要架构 | 占比 | 原文判断 |
| --- | --- | --- |
| 以单 Agent 为主要架构 | **40%** | 基础形态 |
| 开始引入多 Agent | **42%** | 与单 Agent 体量接近 |
| 把 Human-in-the-Loop（HITL，关键步骤必须由人确认后才继续执行）作为**主要架构原则** | **15%** | 不是附加的审批开关，而是架构原则 |

原文结论：「自主度是一个可调参数，混合形态会长期存在。」并与第 1 章、第 12 章的判断互相印证——Chat/RAG、Workflow、Copilot、Agent 与 Managed Agentic Application 在同一家企业内部往往同时存在，**选择取决于任务的确定性程度与容错空间，而非技术新旧**。

值得注意的是 15% 这个数字：把 HITL 当作**架构原则**而不是可选开关，在监管密集行业（金融、医药、审计）是合理默认值。这一条对 MNC 的合规团队尤其有参考价值。

### 1.4 编码先行，但供应商碎片化，尚无事实标准

![图 5 框架与工具渗透：单厂商渗透率头部均低于 40%，Claude Code、AgentScope、Qoder 等分列，尚未出现事实标准](/learn/aliyun-ai-agent-handbook/survey-toolchain.png)

*图：原报告「图 5 框架与工具渗透：头部均低于 40%，尚未出现事实标准」，按城市分列展示**单个框架/厂商的渗透率**（Claude Code、AgentScope、Qoder 等，如 11.4%、10.5%），前十位呈平缓下降而非陡峭长尾。*

> 📌 **本站核对提示**：上图是**单厂商渗透率**口径（任一具体工具的使用比例，头部均不足 40%），下表 57% / 78% 是**「是否采购 / 是否使用」的整体覆盖率**口径（企业是否用了任意一款 Coding 工具或通用框架）。两个口径不同、互不矛盾，引用时请勿混用。

| 工具链渗透 | 占比 |
| --- | --- |
| 企业采购 Claude Code、Codex、Cursor、Qoder 等 Coding 工具 | **57%** |
| 使用通用 Agent 框架 | **78%** |
| 同时在用编程 Agent 与通用 Agent 框架 | **近四成** |

报告给了三条解读，每一条都值得管理者直接抄进立项文档：

- **Coding 是目前唯一实现规模化落地的付费场景**。原因不难理解：反馈信号明确（能否编译、测试是否通过）、环境边界清晰（代码仓库与工作区）、错误代价可控（可回滚）。「这三项恰好是 Agent 稳定运行的前提条件。」
- **还没有出现事实标准**。前十位呈平缓下降而非陡峭长尾，多数企业仍在多框架并行试用。「围绕单一框架构建企业内部标准的做法风险较高。」
- **能力正在互相渗透**。从编程 Agent 沉淀出的工程范式——Skill 的组织方式、工作区隔离、工具调用的权限约束、上下文的分层加载——正在被迁移到企业的办公场景。

另一组落地场景数据：最广泛的是**员工效能、代码工程、数据分析**；而**将 Agent 引入企业核心业务流程的占比不到 40%**。报告对这一排序的解释是「Agent 优先进入可人工兜底的场景」，与 18% 的上线率互相自洽。

### 1.5 上下文与工具：问题不在窗口大小

![上下文、记忆与工具侧痛点分布：按北京、广州、深圳三城分列的柱状图](/learn/aliyun-ai-agent-handbook/survey-context-tool-pain.png)

*图：记忆、上下文与工具侧的痛点分布，按北京、广州、深圳**三城分列**的柱状图（如检索类痛点三城为 51.3% / 53.5% / 44.0%，工具类为 52.6% / 50.9% / 46.6%）。表示「无明显痛点」的受访者不到 10%。下表为报告正文的全国合计口径。*

| 痛点 | 占比 | 白皮书判断 |
| --- | --- | --- |
| 检索不准 | **54%** | 不是靠扩大上下文窗口能解决的问题 |
| 记忆更新与遗忘机制缺失 | **48%** | 同上 |
| 上下文窗口限制 | 排第三 | 排序本身即是结论 |
| 工具过多、选择困难 | **52%** | 工具的组织方式与描述质量，比工具数量更决定调用成功率 |
| 工具幻觉调用 | **50%** | 同上 |
| 表示无明显痛点 | **不到 10%** | — |

另一组数据：**上下文与记忆管理，90% 的企业有明确需求**——这是整份调研中需求覆盖面最广的一项。

**MCP（Model Context Protocol，模型上下文协议）的落地状况**是这一节最值得记住的对比：

| MCP 指标 | 占比 |
| --- | --- |
| 已关注或已落地 MCP（合计） | **37%** |
| 真正完成企业内私有部署 | **9%** |
| 明确提出 MCP 服务管理与注册中心需求 | **28%** |

原文解读非常清楚：「要在企业内真正跑起 MCP，需要私有注册中心、统一身份与鉴权、版本与灰度管理、审计留痕，以及与网关的集成，这些都不是协议规范本身提供的。」28% 的注册中心需求与 9% 的已落地比例形成落差，说明**需求正从认知转向工程实施**。

### 1.6 网关与可观测：多模型路由是最高单项需求

![可观测能力诉求分布：成本归因 50%，排位仅次于全链路追踪，高于审计合规与语义质量监控](/learn/aliyun-ai-agent-handbook/survey-observability.png)

*图：可观测能力诉求分布。成本归因排位高于审计合规，报告称之为「预防性诉求」。*

| 能力诉求 | 占比 | 备注 |
| --- | --- | --- |
| **多模型路由与自动降级**（网关能力） | **63%** | **本次调研中比例最高的单项需求** |
| 成本归因（可观测能力） | **50%** | 仅次于全链路追踪，高于审计合规与语义质量监控 |
| 多 Agent 最大痛点：状态与上下文在多 Agent 协作中衰减 | **60%** | 第二、三大痛点为死锁雪崩与成本失控 |
| 最期待补齐：端侧与开源运行底座 | **73%** | 对运行底座自主可控有明确诉求 |
| 最期待补齐：研发—测试闭环 | **65%** | 多 Agent 的验证成本已被感知为主要负担 |

关于 63% 这个数字，原文的工程判断是关键：「不同任务匹配不同模型、主模型不可用时降级、按成本与延迟动态选择。**这类需求无法在应用代码里逐个解决，需要一个统一的流量入口来承接。**」

关于成本归因，报告的描述是「预防性诉求」：「多数企业 Token 用量还不算大，但已经在为成本的可见性与可分摊做准备……在规模上来之前先建立成本的观测与约束能力，而不是等账单失控后再补。」

### 1.7 评估：最被低估的能力短板

![Agent 评估方法分布：基于 Trace/Trajectory 的自动化评估 6.7%、公开 Agent Benchmark 4.5%、LLM-as-a-Judge 27.8%、基于规则或代码校验 28.8%](/learn/aliyun-ai-agent-handbook/survey-evaluation.png)

| 评估方法 | 占比 |
| --- | --- |
| 人工抽查 | **55%**（稳居第一） |
| 基于运行轨迹（Trajectory）自动评估 | **6%**（报告概述处表述为「不足 8%」） |
| 使用公开 Benchmark | **不到 5%** |
| 尚未建立系统性评估体系 | **28%** |
| 用上 LLM-as-Judge / A-B 实验 / 离线数据集回归任一种 | **34%** |

后果直接体现在任务成功率上：

| 任务成功率 | 企业占比 |
| --- | --- |
| ≥ 90% | **约一成** |
| ≥ 70% | **约 55%** |
| 从未量化过成功率 | **16%** |

原文的判断很锋利：「这部分企业实际上无法判断自己的 Agent 是否在正常工作。」

而正向相关性也被量化了：

> 使用了评估手段的企业中，任务成功率达 70% 以上，是没有评估体系的企业的**约两倍**；而在已上线并持续迭代的企业里，这一比例达 **84%**。

报告给出的因果链是：**评估能力支撑迭代，迭代提升可靠性，可靠性才使持续进行评估成为可能**。反过来，缺乏评估的团队「既无法定位问题，也无法证明改动有效，容易长期停在试点阶段」。

### 1.8 调研报告的总结判断

原文最后一节的标题是「从可行性验证转向可靠性与成本」，三条核心判断：

1. **卡点不是企业意愿，也不是模型能力，而是能优化 Harness 层、开箱即用的工程配套。**
2. **Hybrid 是长期状态，而不是过渡阶段**——单 Agent 与多 Agent 体量接近。
3. **工具与框架选型没有收敛，可迁移的抽象比押注某个具体框架更有价值。**

## 二、核心框架三件套：Agent = Model + Harness

这是全书最需要读懂的一节。白皮书的整个目录结构、责任划分、乃至后面所有章节的存在理由，都从这三件事推导出来。

### 2.1 Agent = Model + Harness

白皮书对 **Agentic Application** 的正式定义：

> _Agentic Application 是 Agent 在应用形态层的完整表达：它以 Model 与 Harness 共同构成的执行主体为核心，与业务逻辑、数据、工具、环境和用户交互相结合，能够围绕业务目标维护上下文与状态、动态规划步骤、采取行动，并在确定性边界内交付可验证的任务结果。_

理解架构的基础公式（原文称之为「非形式化公式」）：

> _**Agent = Model + Harness**_

![Agent = Model + Harness 的两层关系：概念层由 Model 与 Harness 构成 Agent，实现层 Harness 被拆解为一组彼此协同的架构能力](/learn/aliyun-ai-agent-handbook/agent-model-harness.png)

*图 1-1：从 Agent 基础公式到工程架构拆解。上方为概念层（Agent = Model + Harness），下方为实现层——Harness 被拆解为一组彼此协同的架构能力。原图出自第 1 章 1.3.1 节。*

这条公式的价值**首先在于责任边界**，其次才是组件清单。原文的表述值得逐字读：

> Model 提供理解、推理、生成与决策能力，但模型本身不能独立承担上下文准备、任务状态维护、工具执行、权限控制、故障恢复和结果验证。**Harness 是模型之外用于组织、约束并承载模型驱动任务执行的工程系统。**只有二者结合，模型能力才能转化为可持续执行的 Agent。

**Harness 的六类拆解**（广义 Harness 在工程落地中的进一步分解）：

| 能力域 | 具体内容 | 解决什么问题 |
| --- | --- | --- |
| **Agent Loop** | 模型调用、工具调用、结果回送、重试、停止、恢复与预算约束 | 任务怎么推进、什么时候停 |
| **Context、State 与 Memory** | 上下文构建、任务状态持久化、跨会话记忆 | 模型这一步该看见什么、任务事实存在哪里 |
| **Tool、Skill 与 Protocol** | 能力注册、渐进式披露、参数校验、MCP / A2A | Agent 能用什么、怎么被发现和调用 |
| **Runtime 与 Sandbox** | 进程承载、调度、并发、恢复；文件、网络、Secret 隔离 | 任务在哪里跑、影响半径多大 |
| **Observability 与 Evaluation** | Trace、指标、轨迹、评估基线 | 发生了什么、新版本是不是更好 |
| **Security 与 Governance** | 身份、权限、审批、审计、策略 | 谁被允许做什么、出事怎么追责 |

白皮书同时给出三条**反定义**（Harness 不是什么），这三条在实际沟通中比正定义更有用：

- **Harness 不是一个更长的 System Prompt。** Prompt 只是它在某一轮推理中生成的输入之一。
- **Harness 不是某一种 Agent Framework 的同义词。** Framework 可以帮企业实现 Harness，但 Harness 描述的是「Agent 如何工作的系统层」，而不是某一类产品形态。
- **Harness 不是 Runtime 或 Sandbox。** Harness 决定下一步为模型提供什么、允许提出什么行动；Runtime 负责持续承载这个过程；Sandbox 负责把实际行动限制在可控环境中。

第 3 章还给了一张更细的责任分层表：

| 层次 | 核心问题 | 主要责任 |
| --- | --- | --- |
| Model | Agent 能理解和推理到什么程度 | 语义理解、规划判断、生成与工具选择 |
| Harness 编排 | Agent 如何工作 | Loop、Context、State、Plan、Tool、Skill、Subagent、Permission 与 Verification |
| Runtime | Agent 如何持续运行 | 进程承载、任务调度、并发、等待与故障恢复 |
| Sandbox / Environment | Agent 在哪里行动、影响范围多大 | 文件、进程、网络、Secret、资源和环境隔离 |
| Agent Platform | 如何规模化交付和治理 | 多租户、发布、网关、配额、观测、评估、安全和运营 |

原文特别提醒：「这些逻辑边界不一定对应五个独立产品或部署单元……但在架构设计中仍要保留边界，否则企业无法判断故障归属、数据位置、迁移成本和最终责任。」

### 2.2 Agentic Application 的六个判定特征

一个应用是否真的进入了 Agentic 阶段，白皮书给了六条判据（第 1 章 1.3.2）。这是可以直接拿来做**架构评审 checklist** 的东西：

| # | 特征 | 原文表述 |
| --- | --- | --- |
| 1 | **以目标和任务结果为中心** | 用户提供的不再只是一个待回答的问题，而是需要完成的任务和可验收的结果 |
| 2 | **在运行时决定部分执行路径** | 能根据中间结果、工具返回和环境状态调整后续行为，而不是只执行一条完全预编排的路径 |
| 3 | **能够对外部环境产生作用** | 可以调用 API、检索数据、修改文件、运行代码、操作浏览器，或将任务委派给另一个 Agent |
| 4 | **维持跨步骤、跨请求的任务状态** | 任务状态不只存在于一次模型上下文中；需要更长时间运行时还可以暂停、恢复、重试或转交给另一个执行实例 |
| 5 | **自主行为受到确定性机制约束** | 权限、沙箱、预算、中间件、结构化输出、人工审批和失败处理共同构成**模型不能自行绕过**的工程边界 |
| 6 | **通过可观测与评估持续改进** | 不仅保存最终输出，还记录执行轨迹、工具调用、状态变化、资源消耗和人工反馈，使新版本能经过回归、灰度和审批后进入生产 |

原文紧跟一句限定，很重要：「这六项特征是**判断应用架构形态的依据**，而不是必须同时启用的功能清单。」

### 2.3 L1–L4 企业成熟度模型（完整表）

这是全书被引用最多的一张表（第 1 章 1.4.1，表 1-4）。原文对它的定位做了明确限定：「该模型是本白皮书基于**应用架构维度**提出的分析框架，用于判断单个应用的能力形态，**不等同于**以战略、组织、流程和文化为对象的企业 AI 采纳成熟度模型。」

| 成熟度 | 典型应用与运行状态 | 核心能力 | 典型局限 | 升级门槛 |
| --- | --- | --- | --- | --- |
| **L1 辅助生成** | Chat、RAG、基础 Copilot | 内容生成、知识检索、简单工具调用 | 任务闭环由人完成，系统很少维护执行状态 | 建立可复用的 Prompt、知识和基础评测 |
| **L2 受控自动化** | Workflow、在 Workflow 中局部使用 Agent | 预定流程、结构化输出、局部动态决策、审批 | 对未知路径和异常情况的适应性有限 | 明确自主边界，引入 Harness、工具策略和轨迹评估 |
| **L3 Agentic Execution** | 由 Agent 持有任务循环的 Agentic Application（Single-Agent、Long-Horizon Agent 或 Multi-Agent 均可）、Hybrid | 动态规划、工具与环境操作、多步骤任务、持久状态、故障恢复 | 容易在成本、权限、失败放大和版本漂移等方面遇到生产问题 | 建立 Runtime、Sandbox、Observability、Security 和 Evaluation |
| **L4 规模运营与持续优化** | 已实现规模化运行、统一治理和持续优化的 Agentic Application | 多任务与多租户运行、策略控制、可观测、安全、离线与在线评估、灰度和持续优化 | 体系复杂，需要平台、组织和治理能力共同演进 | 通过共享平台、组织知识、标准和自动化降低治理成本 |

**三条必须一起读的限定条件**（否则这张表极易被误用）：

1. **L4 描述的是能力水平，不是一种新的应用形态。** Single-Agent、Long-Horizon Agent 与 Multi-Agent 都可以处于 L3 或 L4——**采用哪种形态取决于任务结构，而处于哪个成熟度取决于运行与治理能力的完备程度**。
2. **不是每个应用都必须依次升级。** 低风险的知识助手可以长期停留在 L1；交易审批系统可以选择 L2，以确定性 Workflow 保持核心路径。
3. **决策原则是「最低充分架构」**：「企业应当结合任务价值、风险、运行规模和工程成本，为每类任务选择**成本与风险可接受的最低充分架构**。」

调研报告对这套分级的对照判断是：「L3 Agentic Execution 仅在部分场景成立，L4 Managed & Optimizing 尚属少数。白皮书构建、运行、治理、调优，本质上都在回答如何从 L2 演进到 L3、L4。」

### 2.4 概念边界表：八个词的界定

白皮书专门做了一张表来划清概念边界（第 1 章 1.3.3，表 1-3）。这张表的实际用途是**跨团队对齐语言**——在立项会、架构评审、供应商评估里，这八个词被混用的成本非常高。

| 概念 | 在本白皮书中的含义 | **不等同于** |
| --- | --- | --- |
| **Model** | 提供语言理解、推理、多模态、生成和工具调用决策能力的概率性认知核心 | 完整 Agent 或完整应用 |
| **Agent** | 由 Model 与 Harness 共同构成，能够围绕目标观察、判断、行动并接受反馈的执行主体 | 任意使用模型的软件，或单独的模型调用 |
| **Harness** | 模型之外，用于组织、约束并承载模型驱动任务执行的工程系统 | 单一 Prompt、简单 Agent Loop，或某个具体 Agent 框架 |
| **Single-Agent** | 由单个 Agent 持有任务循环、在明确任务边界内完成有界任务的基础形态 | 需要跨会话持续执行的单个 Agent 应用（属 Long-Horizon Agent），或只调用一次模型的对话应用 |
| **Long-Horizon Agent** | 能跨多轮、跨会话或跨进程持续执行任务，并通过持久状态、检查点、恢复和人工引导维持任务连续性 | 单纯扩大上下文窗口，或一次持续时间较长的模型调用 |
| **Multi-Agent** | 多个具有不同角色、能力或权限边界的 Agent，通过明确的编排、通信、移交或评审机制共同完成任务 | 简单并发调用多个模型，或将同一任务机械拆成多个提示词 |
| **Agentic Application** | Agent 在应用形态层的完整表达，涵盖 Single-Agent、Long-Horizon Agent 与 Multi-Agent | 单一模型调用、SDK、Agent 框架或共享平台 |
| **Agent Platform** | 为 Agentic Application 提供共享设计、构建、运行、治理和优化能力的企业平台 | 单个业务 Agent 或具体 Agentic Application |

原文强调其中**三个边界尤其重要**：

- **Agent 不等于 Agent 框架。** 框架可以提供 Agent Loop、Tool、Memory 等开发抽象，但框架本身不会自动形成能够围绕目标持续执行、连接业务环境并交付可验证结果的 Agent。
- **Long-Horizon Agent 与 Multi-Agent 不代表天然更高的智能或成熟度。** 长程执行会增加状态漂移、失败恢复和成本控制难度；多智能体协作会增加通信开销，并带来共享状态、失败传播和责任划分问题。
- **应用形态不等于平台形态。** 同一种应用形态既可以依托统一平台运行，也可以采用独立的工程实现。

### 2.5 不同应用形态的横向对照

第 1 章还给了一张形态对照表（表 1-2），比成熟度表更适合做**选型讨论的起点**：

| 应用形态 | 主要价值 | 任务路径 | 状态与执行跨度 | 人的角色 | 典型适用条件 |
| --- | --- | --- | --- | --- | --- |
| **Chat/RAG** | 理解、生成与知识访问 | 由应用预先确定 | 单轮或短会话 | 提问、阅读和判断 | 结果主要是内容，不直接改变外部系统 |
| **Workflow** | 可重复的流程自动化 | 设计时预定，运行时仅有局部分支 | 步骤有限，状态结构明确 | 设计和审批流程 | 任务稳定、路径可穷举、错误代价较高 |
| **Copilot** | 提升人在回路的工作效率 | 由人持续决定目标和下一步 | 可跨多轮，但任务控制权在人 | 驾驶、验收并对结果负责 | 专业判断难以完全自动化，但局部工作可以委托 |
| **Single-Agent** | 由单个 Agent 围绕目标动态完成有界任务 | 由 Agent 在运行时决定部分或大部分路径 | 多步骤、有状态，通常在一次任务或一个会话内闭环 | 定义目标、约束和关键审批点，验收任务结果 | 路径难以预知，环境可提供反馈，结果可验证，任务能在有界时间内完成 |
| **Long-Horizon / Multi-Agent** | 前者持续推进长任务；后者通过分工协作完成复杂目标 | 前者依长期执行反馈动态调整，后者由多个 Agent 通过编排、移交或评审共同决定 | 前者跨会话、跨进程并支持暂停恢复；后者维护多个角色及其任务状态 | 为长程任务设检查点与例外处理，或为多 Agent 设角色、权限与协作边界 | 单 Agent 受时间跨度或角色复杂度限制，且新增收益能覆盖新增复杂度 |

白皮书对 **Workflow 与 Agent 的关系**给了明确判断：二者将长期共存，企业级应用的主流形态是 **Hybrid**——「可以在业务 Workflow 中嵌入 Agent，将不确定性限制在清晰的边界内；也可以由 Agent 调用经过测试的 Workflow 或 Skill，将成熟做法从重复推理中抽离。」

### 2.6 参考架构：三视图 + 五责任域

第 2 章给出厂商中立的企业级参考架构，核心是**三个互相正交的视图**——原文强调「三个视图不能互相推导」：

| 视图 | 回答什么 | 避免什么风险 |
| --- | --- | --- |
| **组件视图** | 系统由什么组成 | 避免能力遗漏（尤其避免把上下文管理、状态持久化、结果验证当成实现细节） |
| **平台视图** | 这些组件在哪里运行，由谁负责 | 避免责任混乱 |
| **生命周期视图** | 系统如何从架构决策走向运行，并在运行中被治理和改进 | 避免把一次性的 Agent 演示误当成可持续运营的企业系统 |

原文举的例子很能说明问题：「同一个 State Store，在组件视图中是任务事实的持久化能力，在平台视图中属于数据与资源面，在生命周期视图中则是运行阶段产生、调优阶段被反复读取的证据来源。」

![Agentic Application 企业级参考架构组件视图：业务与应用层、Agent 构建与编排层、生产运行层、治理和控制层、调优层五个能力责任域](/learn/aliyun-ai-agent-handbook/reference-architecture.svg)

*图 2-1：Agentic Application 企业级参考架构（组件视图）。粗实线表示从业务目标到任务执行的主要关系，虚线表示版本、身份、策略、观测、评估和变更证据等横向作用。*

**五个能力责任域**：业务与应用层 → Agent 构建与编排层 → 生产运行层 → 治理和控制层 → 调优层。原文特别说明：「这里的『层』用于组织架构责任，**不表示严格的调用栈或建设顺序**。」

另外还有一条容易被忽略的强调：**Security 不是只属于调优层的单一组件，而是横跨五层的架构责任**。

**五项企业级架构设计原则**（第 2 章 2.1.3，结合 AWS、Google、Microsoft、Anthropic、LangChain 和 OpenAI 自 2025 年下半年以来的公开实践归纳）：

| # | 原则 | 要点 |
| --- | --- | --- |
| 1 | **Model 与 Harness 解耦** | 模型升级可能使某些补偿性 Prompt、工具或循环控制失效，因此二者必须放在一起评估，但不应在实现上强绑定 |
| 2 | **编排层与 Runtime 解耦** | 才能在不重写任务逻辑的前提下切换托管或自托管 Runtime |
| 3 | **状态外置，执行实例可替换** | 会话、计划、待办、工具结果、工作区、记忆和制品不应只存在于模型上下文或某个 Runtime 的内存中 |
| 4 | **自主性必须与权限和可验证性匹配** | 工具、网络、数据和凭证越多，影响半径（Blast Radius）越大 |
| 5 | **可观测、安全和评估是运行前提，不是上线补丁** | 不记录轨迹和环境结果，不但无法定位问题，也无法复现评估或证明版本改进 |

原文对这五条的收束句很好：「凡是被授予的自主性，都必须有与之匹配的边界、证据和验证手段；凡是暂时不需要的能力，可以不建设，但需要**明确在什么条件下必须补齐**。」

### 2.7 信息五分法：不要用一个上下文包含一切

第 2 章 2.2.3 的这张表（表 2-3）是构建篇的地基，也是最容易在实现中被搞混的地方：

| 对象 | 主要问题 | 典型内容 | 生命周期与一致性要求 |
| --- | --- | --- | --- |
| **Context** | 这一次模型调用应该看到什么 | System Prompt、任务说明、历史摘要、工具描述、检索结果、当前环境状态 | 单次模型调用级，持续被重建，**不作为事实来源** |
| **State** | 任务已经发生了什么，应从哪里恢复 | Session、Task、Plan、Todo、Checkpoint、工具调用状态 | 任务级，需要强一致的事实记录与持久化 |
| **Memory** | 过去哪些交互经验对当前任务有用 | 用户偏好、历史决策、跨会话事实、任务经验 | 跨任务与跨会话，需要写入策略、更新、遗忘与隐私治理 |
| **Knowledge** | 组织已有哪些外部知识可供检索 | 业务文档、规范制度、产品资料、RAG 索引与知识库 | 与组织内容同步，需要权限过滤、时效管理与来源可追溯 |
| **Skill** | 某类任务应该怎么做 | 说明、脚本、模板、Workflow、检查清单与可验证方法 | 作为版本化能力资产发布、复用与回滚 |

原文解释了为什么要把 Memory 与 Knowledge 分列：「Memory 由 Agent 在运行中生成，风险在于**错误经验被反复沿用**，因此需要写入门槛与遗忘机制；Knowledge 来自组织既有内容，风险在于**权限越界与信息过期**，因此需要与源系统的权限模型和更新周期对齐。**把两者放进同一个向量库，往往会同时失去这两类治理能力。**」

最后一句是整节最重要的判断：「必须将可恢复任务的真实状态保存在模型上下文之外：**如果压缩、截断或模型误读能够改变任务事实，任务就失去了可恢复性**，长任务与多智能体协作也无从谈起。」

### 2.8 Agent Release：生命周期的最小可复现单元

![架构设计 → 构建 → 运行 → 治理 → 调优的五阶段生命周期闭环](/learn/aliyun-ai-agent-handbook/lifecycle-loop.png)

*图 2-2：五阶段生命周期闭环。注意由治理和调优指回架构设计的两条虚线——当风险来自形态选择或权限模型本身时，正确动作是重新设计架构，而不是继续叠加补丁。*

白皮书提出一个很实用的概念：**Agent Release**——生命周期的最小发布单元不应只是一份应用代码，而应是一个可复现的组合，至少绑定六类要素：

1. 模型及其版本、参数、推理预算与路由策略
2. Harness 编排代码、配置、循环控制、Middleware 与终止条件
3. Prompt、Context Policy、Memory Policy、Skill 与 Knowledge 版本
4. Tool、MCP 与 Agent 能力清单、权限策略和凭证范围
5. Runtime、Sandbox、资源、网络与数据保留配置
6. 评估数据集、Evaluator、基线、准入阈值和已知风险

原文的警告一针见血：「**如果 Prompt 可以在生产中随时修改而不留版本，任何评估结论都只对当时那一刻成立。**」

白皮书把**架构设计列为生命周期的第一个阶段**（而不是隐含在构建里），理由是：「形态选择、自主性授予、责任域划分和权限边界一旦确定，后续构建、运行、治理和调优的成本区间基本被锁定。把这些决策留给构建阶段隐式完成，等价于**让实现细节反向定义架构约束**，而这类问题往往只能通过重构而非补丁解决。」

还有一条关于治理的自检标准值得贴在墙上：

> 如果某项治理要求只能在上线后通过流程和人工补齐，而不能在架构和构建阶段落到策略、接口或数据结构上，那么它在规模化之后很可能会失效。

### 3.1 架构篇（第 1–2 章）：定义对象、判断形态、选择成熟度

架构篇处理生命周期五阶段中的**第一个阶段**，它给出的是判断与边界：采用什么应用形态、授予多大自主权、哪些能力自建、哪些由共享平台提供、什么结果构成「完成」。官方导读对这一篇的定位很强硬——「这些边界若推迟到构建阶段再确定，后续运行、治理与调优将出现混乱。」

第 1 章解决**对象界定**：应用形态不是一条简单的替代链，Workflow 与 Agent 将长期共存；Single-Agent 沿时间跨度扩展为 Long-Horizon Agent，沿协作结构扩展为 Multi-Agent，两者可独立采用也可组合使用，但**都不是所有应用必经的升级阶段**。成熟度同样不由产品名称决定，判据是自主性能否与任务风险相匹配。

第 2 章解决**结构落位**：三视图互不推导，五责任域，五项设计原则，Agent Release 与五阶段闭环。

官方导读要求读者从这一篇带走两条判断：

> 一、形态与成熟度不由产品名称决定；
> 二、**架构的目的不是把系统做大，而是为每一项被授予的自主性建立对等的执行、观测、安全与评估能力。**

### 3.2 构建篇（第 3–6 章）：Harness 由谁实现 + 三类工程契约

构建阶段的核心工作有两项：**决定 Harness 由谁实现**，以及**把模型的离散判断组织为可持续推进、可中断恢复、可验证结束的任务过程**。

官方导读明确了一条贯穿四章的边界：本篇只**描述并绑定**可用能力，物理执行、状态落盘与环境隔离由运行篇承担。另有一条提醒值得企业注意：Coding Agent 是个好样本，但「审批、交易、客服与运营具有不同的业务状态、权限边界与成功标准，企业应复用其中**可泛化的 Harness 机制**，而非照搬一套 Coding Agent 流程」。

**第一条主线是构建入口的选择**。当前存在四类主要起点——高代码框架、产品化 Harness、Managed Agents、Agent 云产品。原文强调：「四类入口**不构成成熟度阶梯**，也不互斥，选择依据是任务结构、定制深度、数据边界、环境影响、团队能力与交付方式。」当多团队、多来源 Agent 同时存在时，Agent Platform 负责统一创建、接入、交付、运行、治理、协作、观测与优化——**它不是第五类入口**。

**第二条主线把 Harness 拆为任务、信息、行动三类工程契约**，且三者有内在顺序：

> **任务定义流转，信息定义每一步的可见范围，行动定义副作用与验收依据。**

- **任务契约**解决推进与终止：Agent Loop 以 Prepare、Model、Act、Observe、Verify 推进，显式状态与多维预算提供确定性边界，**完成由环境证据判定而非由模型停止判定**。
- **信息契约**解决模型此刻应当看见什么：Context Builder 按身份、可信度、相关性与 Token 预算动态编译输入；任何关键事实必须先落入权威状态。
- **行动契约**解决意图如何成为受控的环境事实：统一 Action Plane 按 Schema、身份、Policy、审批、执行、Observation 与 Trace 推进。

第 4 至 6 章共用同一贯穿案例——**生产服务漏洞修复与变更发布 Agent**，官方建议跨章跟读同一任务。

### 3.3 运行篇（第 7–12 章）：地基与秩序

官方导读用一句话点出了开发与生产的分水岭：「一个在开发环境里跑通的 Agent，与一个对外提供规模化服务的 Agent，要回答的问题并不相同。」而且这些问题在开发阶段同样存在，**区别在于规模掩盖了它们的代价**——「状态没有外置，单人调试时只是重来一次，生产并发下会变成任务丢失、重复执行与无法归因。」

运行篇沿两条主线展开：

- **运行的地基**（第 7–9 章）：解决 Agent 如何**稳定**运行。第 7 章把工具调用扩展为可编程工作空间；第 8 章解决状态外置之后的承载问题——运行时状态、工作区与产物、记忆与知识、业务语义四类对象具有不同的一致性要求；第 9 章把流量入口收敛为统一治理点，**区分 LLM、MCP 与 Agent 三种治理语义**，避免把模型路由、工具协议代理与任务入口混为一层。
- **运行的秩序**（第 10–12 章）：解决多个 Agent 如何**协同**运行。第 10 章界定同步与异步边界，并给出任务完成语义的分层模型，**避免把进程结束当成任务完成**；第 11 章讨论异构 Agent 如何进入同一个团队；第 12 章按能力面、协作面、内构面与人机面给出通信选型地图。

两条主线是递进关系：「**没有稳定运行的单个 Agent，多 Agent 协同只会放大不确定性。**」官方建议第 7、8 章先读。

第 9 章是与调研报告 63% 那个最高单项需求直接对应的一章，值得单独一提。它给出的 AI Gateway 三层划分是全书引用率较高的一个框架：

| 治理语义 | 直接治理对象 | 主要问题 | 不承担的责任 |
| --- | --- | --- | --- |
| **LLM Gateway** | 模型调用及其实际尝试 | 选择哪个模型或端点，如何限流、容灾和计量 | 判断模型输出是否满足业务成功标准 |
| **MCP Gateway** | 工具调用 | Server Registry、凭证托管、工具级 ACL 和审计 | —— |
| **Agent Gateway** | 任务 | Agent 路由、会话连续性、租户配额和预算 | —— |

原文明确说明这三层划分「是本白皮书为区分治理粒度所做的归纳，**并非某一厂商的既有产品定义**」；在具体实现中三者可以是同一 Gateway 的不同能力，「但治理对象和粒度必须区分，否则模型成本、工具权限和任务预算会在同一处策略中互相覆盖」。

第 9 章还有两个容易被忽略的工程细节值得摘出来：

- **SSE 只是传输形式，不能直接充当完整业务事件的边界**——因此 TTFT（Time to First Token，首 token 时延）的统计必须明确起止点，不能简单等同于 HTTP 首字节时延。
- **KV cache 的复用是推理性能优化，不是业务状态恢复**——缓存未命中通常应表现为性能变化，而不应造成业务 Task 丢失。

### 3.4 治理篇（第 13–16 章）：让自主运行的系统变得可信

官方导读开篇是四个问句，很适合直接拿来做治理现状自检：

> Agent 实际执行了什么，我们看不看得见；它会不会越过授权边界，或者被外部内容操纵；它依赖的 Prompt、Skill、MCP、Agent 散落在各处，有没有统一管理；它的行为在上线之前，能不能先验证一遍。

这一篇的定位是：「治理不是给运行额外附加约束的环节，而是让一个已经在运行的系统变得可信。」而且治理沉淀的观测指标、审计证据、资产记录与验证结论，**同时构成调优篇判断问题所依赖的可信事实**——「缺少这一层，改进只能依靠推测。」

四章的依赖关系：**只有第 13 章构成硬依赖**。「没有统一口径的 Trace 与指标，安全事件无法定位到具体步骤，资产变更的影响范围无法度量，验证结论也缺少可比较的基准。」其余三章可按当前关注点选择顺序。

第 14 章的重点在于**区分两种角色**：Agent 既可能被 Prompt Injection 一类手段操纵（被攻击的对象），也可能因自主行动越过边界（自主行动的主体）——防护需要同时覆盖攻击面与授权面。

第 15 章解决的是**规模问题**：「单个应用可以靠团队约定管理能力资产，多团队共用时必须有注册、版本与发布机制，否则**一次 MCP 变更的影响范围无人能答**。」这一章给出的 Agentic Resource Registry，把 Prompt、Skill、MCP Server、Agent 纳入统一注册、版本与按需发现——正是对调研报告中「28% 明确提出 MCP 服务管理与注册中心需求」的直接回应。

第 16 章补上**时间维度**：把验证从上线后观察前移到上线前演练（Agent Simulation），并与 Evaluation、Testing 保持清晰分工。

### 3.5 调优篇（第 17–24 章）：把证据转化为能力提升

调优篇是全书篇幅最长的一篇（8 章），官方导读称它「直接决定前四个责任域的投入能否持续转化为生产收益，也因此是智能体工程中**持续投入最集中的环节之一**」。

这一篇的组织方式**由归因决定**，两条主线加一章专题：

**第一条主线是模型调优（第 17 章）。** 之所以先讨论模型，是因为「模型既是最受关注、也是最容易被误判的优化对象：把本应由上下文、工具协议或运行控制解决的问题当成『模型不行』，往往是**代价最高的一类误判**」。第 17 章因此先建立「何时才应该改模型」的判据：

| 归因对象 | 常见失败情况 | 如何验证 |
| --- | --- | --- |
| **执行环境** | 模型已给出可执行动作，但业务系统、数据服务、Sandbox、计算资源或外部服务无法正常执行 | 绕过模型直接调用相应工具或服务；若故障仍能复现，则归因于执行环境 |
| **Harness** | 模型没有获得必要信息、清晰的工具接口或完整反馈，或状态、重试、停止和权限控制没有被可靠管理 | 固定模型和执行环境，修正上下文、工具协议或运行控制；若问题明显减少，则归因于 Harness |
| **模型** | 信息、动作接口和反馈均充分，执行环境也正常，但模型仍持续作出错误的理解、推理、工具选择、失败恢复或终止决策 | 固定 Harness 和执行环境重复测试或替换模型；若错误跨任务变体稳定出现，或随模型变化显著改善，则归因于模型 |

排查顺序是硬性的：**先排除能独立复现的执行环境故障 → 再检查 Harness 是否提供充分信息与可靠控制 → 最后才判断是否属于模型能力缺口**。

**第二条主线是智能体调优（第 18–23 章）**，核心是**数据飞轮**：把 Trace 组织成可复用的行为轨迹（Trajectory），经声明式 Pipeline 加工成业务样本，沉淀为带判据的黄金数据集，用持续评估与实验发现并验证 Badcase，再通过经验库、Skill、工具与运行机制的优化把验证有效的方法带回运行环境。

**第 24 章是可按需阅读的专题**（边缘运行时与全球优化），与两条主线不互为前提。对有全球业务的跨国企业，这一章的优先级会高于它在目录中的位置。

第 18 章里还有一组很克制的 Benchmark 引用，专门用来说明「为什么企业需要在自己的业务上建立评估」——原文同时标注了日期、配置与原始链接，并明确提醒「这些是各自测试条件下的结果，不代表当前最高分，也不能直接换算为企业业务成功率」。其中特别点出：**OSWorld 2.0 的「部分得分」不等于完整成功率；τ-bench 的 pass⁸ 指同一任务八次执行全部成功，区别于「八次中至少成功一次」的 pass@8**。这种对指标口径的较真，是这本书里比较有价值的部分。

| --- | --- | --- |

## 五、Agentic OS 展望（第 30 章）

这一章是全书争议性最大、也最容易被二手转述扭曲的部分。**先把原文最重要的限定句放在最前面**：

> 我们把这一形态称为 Agentic OS，同时明确它**现在还不是一个已经存在的产品类别，也不必然对应一个新的内核**；它更接近**一组正在成形的系统职责**。

这一句必须保留。任何把「阿里云做出了 Agentic OS」当作结论的转述都是失真的。

### 5.1 五项已确立的架构共识

第 30 章先回顾前六篇收敛出的五项相对稳定的结论：

| # | 共识 | 出处与含义 |
| --- | --- | --- |
| 1 | **架构对象是系统，不是一次模型调用** | 第 1 章拆 Model + Harness，第 2 章分五个能力责任域。意义在于责任归属——**模型升级不应变成应用重构，任务语义不应与基础设施强绑定** |
| 2 | **任务是需要被长期管理的对象** | 一个 Agent 任务的生命周期**长于一次请求、宽于一个进程**，可能跨越多个副本与区域，因此状态必须外置，且必须可以被暂停与恢复 |
| 3 | **能力是动态接入的，能力发现与执行授权必须分开** | 「模型知道某个工具存在，与模型有权执行该操作，是两件必须分别设计的事」 |
| 4 | **自主性必须与权限、可撤销范围和可验证性匹配** | 授予的自主权越大，影响半径越大，与之匹配的边界与证据要求也越高 |
| 5 | **证据是变更能否发布的前提** | 任何一次 Agent Release，无论改的是 Prompt、Skill、工具、模型还是 Harness，都需要以**可复现的评估结果**作为发布依据 |

### 5.2 六类跨章节反复出现的工程约束

这五项共识在单个应用内可以落地，困难出现在组织层面。当同一家企业同时运行多个 Agent、使用多种框架、服务多个租户时，六类约束会在每个应用内被重复实现一次，且实现方式互不一致：

1. **任务缺少统一的标识与状态归属**——各框架对「一次运行」的语义并不相同：有的以会话为单位，有的以图执行为单位，有的以进程为单位。
2. **执行环境成为一等资源，其成本决定并发经济性**——按峰值为每个任务预留资源会留下大量空闲配额，按平均值部署则会在集中编译、测试或读取数据时产生拥塞。
3. **能力元数据不足以支撑自动化决策**——生产中真正稀缺的是三类声明：**该操作是否有外部副作用、是否幂等、失败后是否可安全重试**。
4. **上下文与状态的边界容易被侵蚀**——压缩、摘要与续行会不断把「不完整的对话历史」当成「可恢复的任务事实」。
5. **授权难以随任务派生与收回**——「任务已终止」与「该任务的凭证已失效」并不总是同时成立。
6. **证据的采集点分散，口径不统一**——跨应用的成本核算、故障定位与质量回归都缺少可比性。

### 5.3 三条下沉判据与 Agentic OS 的窄定义

并非所有共性能力都应该下沉。白皮书提出三条判据——**一项能力只有同时满足判据一，且至少满足判据二或判据三，才具备下沉到系统层的理由**：

| 判据 | 含义 | 属于此类 | 不属于此类 |
| --- | --- | --- | --- |
| **一、复用性** | 多个应用会重复实现该能力，且实现方式差异不产生业务价值 | 工作区快照、沙箱创建、Trace 采集 | 任务的终止条件与验收标准 |
| **二、强制性** | 该能力必须由**被约束方之外**的组件执行，才能真正生效 | 权限校验、网络出站控制、预算上限、审计记录 | 只写在提示词里、或由被约束的 Agent 自己调用的约束 |
| **三、可验证性** | 该能力需要**独立于执行方的证据来源**，才能被采信 | 模型调用与系统行为的关联观测、工作区状态的独立校验 | 由 Agent 自行上报的执行结果 |

据此，白皮书给出 Agentic OS 的**窄定义**：

> _Agentic OS 是为 Agent 任务提供公共运行对象、公共能力接入、可强制边界与统一证据的系统层。它以任务、环境、能力、授权与证据为核心管理对象，**不持有任务语义**。_

定义包含三条否定，原文明确说「它们与定义本身同样重要」：

1. **Agentic OS 不替代 Harness。** 模型看什么、能调用什么、什么时候停、结果如何验收——这些属于任务语义，应留在应用侧。
2. **Agentic OS 不等于又一个 Agent 框架。** 「框架的约束在不使用该框架时即失效，**系统层的约束应在被约束方不配合时仍然成立**。」
3. **Agentic OS 不必然意味着修改内核。** 「下沉的目标是让能力位于被约束方之外，而不是位于尽可能低的层次……**能力放在哪一层，取决于它在该层能否真正生效，而不取决于它听起来是否更底层**。」

### 5.4 九类核心管理对象

传统操作系统管理进程、地址空间、文件与设备；Agentic OS 若要成立，必须说清它管理什么。白皮书归纳了九类：

| 管理对象 | 语义 | 既有系统中的近似物 | 缺失时的后果 |
| --- | --- | --- | --- |
| **Agent 身份** | 可被授权、可被审计的执行主体 | 服务账号、独立标准账户 | 无法区分 Agent 与用户的操作责任 |
| **Run（任务运行）** | 一次有目标、可暂停、可恢复的执行 | 进程组、作业、工作流实例 | 跨框架无法统一计量、限流与排障 |
| **Session** | 交互与上下文的连续性载体 | 会话、连接 | 上下文历史被误当作任务事实 |
| **Workspace** | 任务可读写的文件与制品空间 | 目录、卷、容器层 | 并发任务互相污染，失败后无法回退 |
| **Skill** | 可复用、可发布、可校验的行动方法 | 脚本、软件包 | 能力沉淀不可审计，也无法回滚 |
| **Tool 与 MCP 端点** | 可发现、可调用的外部能力 | 系统调用、API、服务 | 能力发现与执行授权混同 |
| **Budget Lease（预算租约）** | 有上限、有期限、可收回的资源与调用额度 | 配额、cgroup 限额 | 预算失控，且子任务无法被约束 |
| **Policy** | 可强制执行的边界声明 | 访问控制、seccomp、网络策略 | 约束只存在于提示词中 |
| **Evidence（证据）** | 计划、已发出操作与已确认结果的记录 | 日志、审计记录 | 无法证明变更改进，也无法安全重试 |

三个对象值得单独理解：

- **Run 与进程不是同一层次的对象。** 「它的正确性依据不是『进程是否存活』，而是『**任务事实是否完整且一致**』。」
- **Budget Lease 是最容易被忽略、但对可控自治最关键的对象。** 租约模型把「配额」与「最小权限」合并为同一件事：一次授权同时限定可用资源、可执行操作、有效期限与撤销方式，并可随子任务派生。
- **Evidence 必须区分三种状态**：计划中的操作、已发出的操作、已确认结果的操作。原文举的例子极具工程说服力——「以『修改配置后重启远程服务』为例，恢复本地工作区文件并不会把远程服务恢复到原状态；若之前的调用已经发出但结果未返回，直接重试还可能重复产生影响。」

### 5.5 自治阶梯：上限由可撤销范围决定，不由模型能力决定

第 30 章给出的这张表（表 30-4），是全书最适合直接放进治理制度文档的一张：

| 级别 | 系统行为 | 新增的边界要求 | 新增的证据要求 |
| --- | --- | --- | --- |
| **L1 建议** | 生成命令或方案，由人执行 | 无需执行权限 | 建议内容可追溯 |
| **L2 单步获准执行** | 每次变更前请求批准 | 操作与资源一一对应的授权 | 每次执行的输入、输出与批准记录 |
| **L3 有界自主** | 在限定资源、预算与操作集内连续执行 | 预算租约、工作目录限定、读写分离 | 完整调用轨迹与预算消耗 |
| **L4 长任务自主** | 跨会话长期执行，可暂停与恢复 | 可级联撤销的授权、可回退的工作区 | 计划、已发出操作与已确认结果的区分 |
| **L5 组织级自治** | 跨系统、跨团队委派与协作 | 可验证的委派链、跨域强制点 | 跨组织可审计的责任归属证据 |

原文的隐含判断值得完整引用：

> **自治程度的上限不由模型能力决定，而由可撤销范围与可证明范围决定。**当一项操作既不能撤销，也不能证明其结果，那么无论模型多可靠，把它交给自主执行都缺少工程依据。

### 5.6 强制边界 vs 观测边界：一句可以被检验的话

这一节（30.6.2）是全书对供应商宣传最具杀伤力的部分。白皮书要求在架构文档与产品说明中严格区分两类边界：

> 一项边界**只有在满足下列全部条件时**，才能称为**强制边界**：覆盖任务入口、凭证获取、网络与 DNS 访问、文件与进程间通信、子进程创建、原生工具调用、后台任务与子 Agent、以及交互控制台等**全部可用路径**；在判定组件不可用时采取**失败即拒绝（fail-closed）**的行为；并且通过**负向测试**证明绕过尝试确实被拒绝。任何一条不满足，该边界只能称为**观测边界**，即能够发现越界行为，但不能阻止它。

同理：「『只读接入』是一个**需要证明的结论**，而不是一个可以声明的属性。只有通过『写路径不可达』的负向测试，才能称某个接入是只读的。缺少该测试时，准确的表述是『**未观察到写操作**』。」

对应的四类接入能力分级：**外部边界强制 / 包装器中介 / 仅观测 / 不支持**。原文要求描述接入能力时同时给出四个维度（强制属性还是观测属性、覆盖的操作语义、覆盖的执行路径、证据质量），理由是：

> 这样描述的价值在于，它使「我们已纳管某类 Agent」成为**一句可以被检验的话**。

### 5.7 效能指标的三段式披露口径

第 30 章 30.5.2 节还提出了一个应当被行业采纳的披露规范。原文以 ANOLISA 对 Token-less 压缩效果的披露方式为样本：它区分组件级基准与单次观测值，并同时声明三条边界（节省只作用于进入上下文的工具响应，不等于整场会话账单；结果随负载变化；效果估算方法另有文档）。白皮书据此给出判断：

> 本书认为这种「**数字 + 适用范围 + 测量来源**」的三段式披露，应当成为 Agent 相关效能指标的默认口径。反过来说，**缺少适用范围与测量来源的单一百分比，无论数值多高，都不具备跨实现比较的价值**。

这条口径同样适用于评估白皮书自己所属厂商的商业宣传数字——见文末阅读提示。

### 5.8 七个开放问题

第 30 章最后列了七个当前没有公认答案的问题，并为每一个给出「判断进展的标志」，便于读者在未来一到两年自行校准：

| # | 开放问题 | 判断标志 |
| --- | --- | --- |
| 1 | Run 对象应该落在哪一层 | 是否出现被多个框架共同采用的任务状态语义，且在框架不配合时仍能被宿主观测与约束 |
| 2 | Agent 身份与委派链如何跨组织传递 | 是否出现可被独立第三方验证的委派凭证格式，以及配套的撤销机制 |
| 3 | 副作用与幂等性能否成为可机读的能力元数据 | 主流工具协议是否引入相关字段，且运行时确实依据这些字段改变重试行为 |
| 4 | 沙箱与工作区的成本与隔离曲线最优点 | 是否出现同时公开创建吞吐、空载占用、恢复时延与隔离强度的可复现测评 |
| 5 | 共享状态如何做到既复用又不越界 | 分域机制是否成为默认配置而非可选项，以及是否有对应的越权检测手段 |
| 6 | 评估如何从离线数据集走向系统级基准 | 是否形成在相同负载、权限与服务目标下同时评价质量、成本与安全的公开方法 |
| 7 | 自进化的变更边界 | 是否出现被广泛接受的变更分级与准入规则 |

第 3 条尤其值得中国区企业关注——白皮书自己的判断是「这是当前**最欠缺、且收益最直接**的一类元数据：它决定重试与补偿能否自动化，也决定审批策略能否按风险分级而不是按工具名单配置」。

## 六、给中国区企业与跨国公司的启示（本站观点）

> **以下内容为本站（aidigest.club）基于白皮书数据的延伸判断，不是原文观点。**原文数据已在上文逐条标注出处，本节的推论责任由本站承担。

### 6.1 18% 的生产化率 = 落地鸿沟，而鸿沟就是咨询空间

调研最锋利的一组对照是：**46% 在开发，18% 上生产，不到 10% 持续迭代。**再叠加地域 × 规模的交叉数据——上海大型企业上线率 45%、小微 16%，深圳 38% 对 17%。

白皮书自己的归因是「差异并不在是否愿意投入，而是是否具备持续演进 Agent 的工程能力」。把这句话翻译成商业语言：

> **28 个百分点的上线率差距，不是模型差距，不是预算差距，是工程能力差距。而工程能力是可以被外部供给的。**

这对咨询与系统集成服务商意味着几件具体的事：

1. **不要再卖「Agent 能做什么」，要卖「Agent 怎么上生产」。** 客户已经过了可行性验证期——46% 在做，说明 POC 阶段的销售叙事已经失效。真正的需求在 46% 到 18% 之间那 28 个点。
2. **交付物的重心从模型选型转向 Harness 工程配套。** 白皮书的总结判断原话是「卡点……是能优化 Harness 层开箱即用的工程配套」。上下文与记忆管理（90% 有明确需求）、评估基建、多模型治理，这三项是需求最集中的交付物。
3. **大型企业与中小企业需要不同的打法。** 45% vs 16% 的差距说明，大型企业缺的是规模化治理（L3→L4），中小企业缺的是从 0 到 1 的工程底座（L2→L3）。用同一套方案覆盖两端，两边都不讨好。

### 6.2 63% 的多模型路由诉求 = AI 网关是刚需，对 MNC 尤其成立

**多模型路由与自动降级是本次调研中比例最高的单项需求（63%）。**白皮书的工程判断是「这类需求无法在应用代码里逐个解决，需要一个统一的流量入口来承接」。

对跨国公司来说，这条结论的分量还要再加两个数量级，因为 MNC 面对的是白皮书没有展开、但在中国区实际存在的三重约束：

- **境内外模型混用是常态。** 境外总部的标准可能是 Claude / GPT / Gemini，中国区实际可用的是通义、豆包、DeepSeek、智谱等。应用代码里写死任何一边，都会导致中国区分支要维护一套 fork。
- **合规隔离不是可选项。** 数据出境、模型服务落地、审计留痕的要求，本质上要求一个能在流量入口处做**策略判定与证据采集**的组件，而不是散落在各应用里的 if-else。
- **成本归因要能按区域/法人主体切分。** 调研中成本归因需求占 50%，对 MNC 而言这不只是财务视角，还涉及转移定价与内部结算。

白皮书第 9 章把 AI Gateway 从「流量入口」扩展为「统一治理入口」（集中承接工具注册与检索、参数校验、模型路由、熔断重试、链路追踪与成本标签），并区分 LLM / MCP / Agent 三层治理语义——**这套划分对 MNC 的中国区架构设计有直接的参考价值**，因为它把「合规隔离」从一个组织流程问题，变成了一个可以被落到接口与策略上的工程问题。

一句可执行的建议：**在中国区做 Agent 架构，AI 网关应当是第一个建、而不是最后一个补的组件。**因为它既是模型可替换性的保证，也是合规证据的采集点——这两件事都不适合事后加装。

### 6.3 评估自动化不足 8%，是整份调研中最被低估的短板

这是本站认为整份调研里**信号最强、但最容易被忽略**的一组数据：

- 55% 靠人工抽查
- 能基于运行轨迹自动评估的只有 6%（概述处表述为「不足 8%」）
- 16% 从未量化过任务成功率
- 任务成功率 ≥90% 的企业**仅约一成**

而正向数据同样有力：用上评估手段的企业中，成功率达 70% 以上的比例是无评估体系企业的**约两倍**；在已上线并持续迭代的企业里达到 **84%**。

为什么说它被低估？因为**评估是唯一一个「不做也能上线、但不做就永远无法改进」的能力**。它不像模型选型那样有明确的采购决策点，也不像网关那样在故障时会疼——它的缺失表现为**长期停在试点阶段却说不清原因**。

三条具体建议：

1. **把「任务成功率」作为 Agent 项目的第一 KPI，而不是「上线了几个 Agent」。** 16% 从未量化过成功率的企业，本质上在盲飞。
2. **评估基建要在第一个 Agent 上线前建，不是第十个。** 白皮书第 2 章的原则五说得很清楚——「可观测、安全和评估是运行前提，而不是上线补丁」。补丁式评估的最大问题不是成本，而是**没有历史基线，任何改进都无法被证明**。
3. **对供应商提出「三段式披露」要求。** 借用白皮书自己提出的口径：数字 + 适用范围 + 测量来源。任何一个孤立的百分比，无论多高，都不具备跨方案比较的价值。这条同样适用于评估白皮书发布方自己的商业产品数字。

### 6.4 可迁移的工程抽象 > 押注单一框架

调研数据支持一个反直觉的选型结论：**市场尚未形成寡头格局，供应商呈现碎片化。**

- 采购 Coding 工具 57%、使用通用 Agent 框架 78%、近四成两者并用
- 「前十位呈平缓下降而非陡峭长尾，多数企业仍在多框架并行试用」
- 原文结论：「**围绕单一框架构建企业内部标准的做法风险较高。**」

白皮书全书的组织方式本身就是这一判断的产物——它以 Harness 作为核心抽象，把 Skill、Memory、Knowledge、Tool 作为可组合能力分别成章，明确目的是「给出一套**不绑定具体框架**的构建范式」。

对企业架构师的三条落地建议：

1. **把 Agent Release 六要素作为内部标准，而不是把某个框架作为内部标准。** 模型版本、Harness 配置、Prompt/Context/Skill 版本、能力清单与权限、运行环境配置、评估基线——这六项是框架无关的，且换框架时不需要重写。
2. **状态外置是最高优先级的解耦动作。** 原则三「状态外置，执行实例可替换」是四个解耦面里唯一已经形成共识、且能立刻执行的一条。状态一旦外置，换框架的成本就从重写降为重接。
3. **用「能否在不重写任务语义的前提下完成替换」检验解耦是否成立。** 白皮书对解耦给出的判据不是「是否存在接口定义」，而是「**是否能在不重写任务语义的前提下完成替换，并用同一套评估证明替换后的行为在可接受范围内**」——注意这句话把评估变成了解耦的**前提条件**，而不只是质量保障手段。

### 6.5 一条容易被忽略的组织启示：HITL 是架构原则，不是审批开关

15% 的企业把 Human-in-the-Loop 作为**主要架构原则**来设计，而不是当作附加的审批开关。对受监管行业（金融、医药、审计、法务）的中国区业务与 MNC 合规团队，这个数字比 40% / 42% 的单 vs 多 Agent 之争更值得关注。

配合第 30 章的自治阶梯表（L1 建议 → L5 组织级自治），可以得到一个很实用的治理框架：**不要用「Agent 成熟度」谈自动化程度，要用「可撤销范围 + 可证明范围」谈**。这两个维度都是可以写进制度文件、可以被审计检验的，而「模型够不够聪明」不是。

**但以下章节与阿里云商业产品高度对应，阅读时需要做「架构建议 vs 产品叙事」的切分：**

| 章节 | 对应商业产品线 | 阅读建议 |

**关于商业承接：**同日（2026-09-22）云栖大会上，阿里云 CTO 李飞飞发布了 Agentic Cloud 战略与企业级 Agent 构建治理平台 **AgentCore**（含 AgentRun、AgentTeams 等能力），另有 Agent Sandbox、新一代 CPFS 等产品。白皮书与 AgentCore 的关系，本质上是**方法论与商业承接的一体两面**——这不影响方法论本身的价值，但影响如何解读其中的「最佳实践」。

**关于流传较广的两个数字，必须标注口径：**

> 「任务完成率提升 99%」「TCO 降低 70%」——这两个数字出自阿里云 2026-09-22/23 的 AgentCore 发布通稿与媒体转载，属于 **vendor-claimed（厂商自述），未经独立第三方验证**。
>
> 需要注意三点：
> 1. **这两个数字不在白皮书正文中。**本站已核对全书 52 个 md 文件，未检索到对应表述——它们来自产品发布materials，不是白皮书结论。
> 2. **口径不明确。**通稿中「TCO 下降可达 70%」的语境是「临时探索的分支可以在完成后释放……显著降低 Agent 长时任务中的闲置算力成本」，即**特定负载模式下的闲置算力节省**，不等于 Agent 项目整体 TCO。「提升任务完成率 99%」在不同转载中表述为「任务完成率超 99%」「提升 99%」，两者含义完全不同。
> 3. **按白皮书自己的标准，这两个数字都不合格。**第 30 章 30.5.2 节要求的披露口径是「数字 + 适用范围 + 测量来源」三段式，并明确说「缺少适用范围与测量来源的单一百分比，无论数值多高，都不具备跨实现比较的价值」。
>
> **本站建议：引用时必须标注为厂商自述并说明口径，不要作为独立事实转述。**

**最后一条阅读建议**：这本书最值得读的不是它给的答案，而是它划的边界——「Harness 不是什么」「Agentic OS 不是什么」「强制边界与观测边界的区别」「协议兼容不等于能力等价」。这些否定性判断在采购评估、架构评审和供应商答辩时的实用价值，高于任何一个正面框架。
